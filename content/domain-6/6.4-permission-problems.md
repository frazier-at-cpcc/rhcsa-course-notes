### Read the error first
- The objective: ==diagnose and correct file permission problems==
- Access passes through four layers, and any one can refuse
- The error text narrows it down
  - ==Permission denied==: mode bits, an ACL, or SELinux
  - ==Operation not permitted==: a file attribute such as immutable, or an action only root may take
- Work from the top of the path down, and change one thing at a time

:::figure wide 6.4-permission-order.svg | Each layer can only take access away. Root skips the mode and ACL check, but not the attributes or SELinux.

### Walk the path
- A file is unreachable if any parent directory lacks ==x== for you
- ==`namei -l path`== lists owner, group, and mode for every component; the first `Permission denied` marks the blocker
- Then compare with ==`id`==: which of those groups are yours?

```console label="Terminal"
$ cat /srv/devops/releases/notes.txt
cat: /srv/devops/releases/notes.txt: Permission denied
$ namei -l /srv/devops/releases/notes.txt
f: /srv/devops/releases/notes.txt
drwxr-xr-x root root   /
drwxr-xr-x root root   srv
drwxr-x--- root devops devops
                        releases - Permission denied
$ id
uid=1001(student) gid=1001(student) groups=1001(student),10(wheel) context=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
```

- `/srv/devops` is `750 root:devops`, student is not in devops, so the other bits (`---`) apply

### Group membership and when it applies
- Add the user to the group: ==`usermod -aG devops student`==
  - Without `-a`, `-G` replaces every supplementary group the user had
- A process gets its group list at ==login== and keeps it
  - A shell opened before the `usermod` still lacks devops; `id` there shows the old list
  - ==`id student`== reads `/etc/group`, so it shows the new group at once
  - Each captured command ran in a fresh login, so it already had devops
- Three ways to pick up the change
  - Log out and back in (or `su - student`)
  - ==`newgrp devops`==: a new shell with devops added
  - ==`sg devops -c 'cmd'`==: one command with devops

```console label="Terminal"
$ sudo usermod -aG devops student
$ id student
uid=1001(student) gid=1001(student) groups=1001(student),10(wheel),1004(devops)
$ sg devops -c 'cat /srv/devops/releases/notes.txt'
v1
```

### Directories need x, files need w
- `x` on a directory lets you pass through; `r` lets you list
  - At `710`, the group opens a known file but cannot list
- Appending needs `w` on the file; creating or deleting needs `w` and `x` on the directory

```console label="Terminal"
$ sudo chmod 710 /srv/devops
$ sg devops -c 'ls /srv/devops; cat /srv/devops/releases/notes.txt'
ls: cannot open directory '/srv/devops': Permission denied
v1
$ sudo chmod 750 /srv/devops
$ sg devops -c 'echo v2 >> /srv/devops/releases/notes.txt'
sh: line 1: /srv/devops/releases/notes.txt: Permission denied
$ sudo chmod 660 /srv/devops/releases/notes.txt
$ sg devops -c 'echo v2 >> /srv/devops/releases/notes.txt'
$ cat /srv/devops/releases/notes.txt
v1
v2
```

### ACLs and the mask
- An ==ACL== adds entries for named users and groups beyond u, g, and o
  - `setfacl -m u:alice:r file`; read back with ==`getfacl`==
  - A `+` after the mode in `ls -l` means an ACL is present
- The ==mask== caps every named entry and the owning group
  - With an ACL, the group column of `ls -l` shows the mask, not `group::`
  - `chmod g=...` rewrites the mask, so a later `chmod 600` silently cancels alice's entry
- `getfacl` flags the damage with ==`#effective:`==

```console label="Terminal"
$ sudo setfacl -m u:alice:rx /srv/devops /srv/devops/releases
$ sudo setfacl -m u:alice:r /srv/devops/releases/notes.txt
$ ls -l /srv/devops/releases/
total 4
-rw-rw----+ 1 root devops 6 Oct 21 19:18 notes.txt
$ sudo chmod 600 /srv/devops/releases/notes.txt
$ sudo getfacl /srv/devops/releases/notes.txt
# file: srv/devops/releases/notes.txt
# owner: root
# group: devops
user::rw-
user:alice:r--	#effective:---
group::rw-	#effective:---
mask::---
other::---
$ sudo -u alice cat /srv/devops/releases/notes.txt
cat: /srv/devops/releases/notes.txt: Permission denied
```

- Repair the mask: `setfacl -m m::rw file`, or `chmod g+rw file`
- `setfacl -x u:alice file` removes one entry; `setfacl -b file` removes the whole ACL

### Attributes and SELinux
- An ==immutable== attribute (`chattr +i`) blocks every change, even from root
  - `lsattr` shows an `i`; `chattr -i` clears it
  - `chattr +a` (append-only) allows `>>` but not overwrite or delete

```console label="Terminal"
$ sudo chmod 666 /srv/devops/releases/notes.txt
$ sudo chattr +i /srv/devops/releases/notes.txt
$ sudo lsattr /srv/devops/releases/notes.txt
----i----------------- /srv/devops/releases/notes.txt
$ echo v3 | sudo tee -a /srv/devops/releases/notes.txt
tee: /srv/devops/releases/notes.txt: Operation not permitted
v3
$ sudo chattr -i /srv/devops/releases/notes.txt
$ ls -Z /srv/devops/releases/notes.txt
unconfined_u:object_r:var_t:s0 /srv/devops/releases/notes.txt
```

- ==SELinux== is checked after the mode bits pass
  - Mode `666` above, yet a confined service such as httpd could still be refused this `var_t` file
  - Look for a denial: `ausearch -m AVC -ts recent`
  - Fix the label with `semanage fcontext` and `restorecon` (objective 10.5); `chcon` alone is lost at the next relabel
- Never "fix" a denial with `chmod 777`; find the layer that refuses

:::wide
| Symptom | Check | Correct it with |
|---|---|---|
| Denied on a file whose own mode looks fine | `namei -l` | `chmod` the parent directory that lacks `x` |
| User added to a group, still denied | `id` in that shell, `id user` | new login, `newgrp`, or `sg` |
| ACL entry has no effect | `getfacl`, look for `#effective` | `setfacl -m m::rw` |
| Root gets Operation not permitted | `lsattr` | `chattr -i` |
| Service denied, mode and ACL look right | `ls -Z`, `ausearch -m AVC` | `semanage fcontext`, `restorecon` |
:::

- Every fix here is stored on disk, so it survives a reboot

:::exam
- A task says a user "cannot write to /srv/devops". Check the whole path and the user's groups before touching modes; the fix is often one missing `x` or a missing group membership.
- If a named ACL entry looks right but does not work, read `#effective` in `getfacl`: the mask is cutting it.
- The grader logs in fresh, so a group change counts once it is in `/etc/group`. To test it yourself, log in again or use `newgrp`.
:::

:::
