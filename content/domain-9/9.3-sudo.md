### Three ways to act as root
- The objective: ==configure privileged access==
- ==Root login==: sign in as root at the console or over SSH
  - The RHEL 10 installer disables the root account by default and asks for an administrator user instead
  - Password SSH logins as root are off by default (10.3)
- ==su==: switch to another user with that user's password
  - `su -` with no name means root, so it needs the root password
- ==sudo==: run one command as root with your own password, if a rule allows it
  - Every command is logged with the user's name; nobody shares the root password
- To configure privileged access on the exam, you write sudo rules

```console label="Terminal"
$ sudo passwd -S root
root L 2025-06-05 0 99999 7 -1
```

- `L` means locked: no password login for root until someone runs `sudo passwd root`

### The wheel group
- RHEL ships one rule that matters: members of ==wheel== may run anything as anyone
  - They type their own password, then sudo caches it for 5 minutes
- Granting full admin rights is a group change, not a sudoers edit

```console label="Terminal"
$ sudo grep -E '^[^#]*wheel|includedir' /etc/sudoers
%wheel	ALL=(ALL)	ALL
#includedir /etc/sudoers.d
$ sudo -l -U alice
User alice is not allowed to run sudo on servera.
$ sudo usermod -aG wheel alice
$ sudo -l -U alice | tail -2
User alice may run the following commands on servera:
    (ALL) ALL
```

- The `#includedir` line is a directive, not a comment: it loads every file in `/etc/sudoers.d`
- The user must log in again before the new group counts

### Editing safely with visudo
- Never edit `/etc/sudoers` with a plain editor; use ==visudo==
  - Locks the file, opens it in `vi` (or `$EDITOR`), and checks the syntax before saving
  - On an error it offers to re-edit, so a typo cannot lock everyone out of sudo
- Prefer a ==drop-in== file in ==/etc/sudoers.d/== over changing `/etc/sudoers`
  - `sudo visudo -f /etc/sudoers.d/webops` edits or creates one
  - One file per team or task: easy to review, copy to another server, or delete
  - Mode `0440`, owner root
  - File names containing a dot or ending in `~` are skipped: `webops.conf` is silently ignored
- Check every file without editing: `visudo -c`; check one: `visudo -cf file`

```console label="Terminal"
$ sudo visudo -cf /etc/sudoers.d/broken
/etc/sudoers.d/broken:1:32: syntax error
%webops ALL=(root) NOPASWD: ALL
                               ^
```

- A broken file written with `tee` or `echo` bypasses that check
  - sudo on RHEL 10 still runs the other rules but prints the parse error on every call
- sudo reads its files on every run: no service to restart, and rules persist across reboots

### Writing rules: command restrictions and NOPASSWD

:::wide
| Who | Host | `=(` Run as `)` | Tag | Commands |
|---|---|---|---|---|
| `alice` or `%webops` (a group) | `ALL` | `(root)` or `(ALL)` | `NOPASSWD:` (optional) | `ALL`, or full paths with optional arguments |
:::

- A ==command restriction== lists full paths, with arguments if you want to pin them
  - `/usr/bin/systemctl restart httpd` allows exactly that; `/usr/bin/systemctl` alone allows any arguments
  - `Cmnd_Alias` names a list so the rule stays readable
- ==NOPASSWD:== skips the password prompt for the commands after it
  - Common for automation accounts; a task will say "without a password"

```text label="/etc/sudoers.d/webops"
# Web team: manage httpd only, no password
Cmnd_Alias WEB = /usr/bin/systemctl restart httpd, \
                 /usr/bin/systemctl reload httpd, \
                 /usr/bin/systemctl status httpd
%webops ALL=(root) NOPASSWD: WEB
```

```console label="Terminal"
$ sudo chmod 440 /etc/sudoers.d/webops
$ sudo visudo -c
/etc/sudoers: parsed OK
/etc/sudoers.d/student: parsed OK
/etc/sudoers.d/webops: parsed OK
```

- ==sudo -l== lists your own rules; `sudo -l -U bob` lists another user's (root only)
- `sudo -l command` answers "would this be allowed?" and prints the full path if yes

```console label="Terminal (as bob)"
$ sudo -l systemctl restart httpd
/bin/systemctl restart httpd
$ sudo -l systemctl stop httpd; echo "exit $?"
exit 1
```

- A command outside the rule is refused after the password prompt
  - `Sorry, user bob is not allowed to execute '/bin/dnf -y install nmap' as root on servera.lab.example.com.`

### su versus sudo

| Command | Password | Result |
|---|---|---|
| `su -` | root's | root login shell |
| `su - alice` | alice's | alice's login shell |
| `su alice` | alice's | alice, but your directory and variables |
| `sudo cmd` | yours | one command as root |
| `sudo -u alice cmd` | yours | one command as alice |
| `sudo -i` | yours | root login shell |
| `sudo -s` | yours | root shell, current directory |

- The `-` (or `-l`) in `su -` runs the target's login scripts: its `PATH`, its home, its umask
  - Plain `su` keeps your environment, which breaks commands that rely on root's `PATH`
- From root, `su - alice` needs no password: a quick way to test as that user

```console label="Terminal"
$ sudo -i pwd; sudo -s pwd
/root
/home/student
$ sudo su - alice -c pwd; sudo su alice -c pwd
/home/alice
/home/student
```

:::exam
- "Members of group sysadmin can run any command with sudo" is `%sysadmin ALL=(ALL) ALL` in a drop-in under `/etc/sudoers.d`. Add "without a password" and it becomes `NOPASSWD: ALL`.
- A user-specific rule names the user with no `%`. A group rule without `%` silently matches a user of that name instead.
- Always finish with `visudo -c` and `sudo -l -U user`. A drop-in named with a dot, or a syntax error, leaves the rule unused.
:::
