### Reading ls -l
- The objective: ==list, set, and change standard ugo/rwx permissions==
- Every file has one ==owner== (user), one ==group==, and three permission sets
  - ==u== the owner, ==g== members of the file's group, ==o== everyone else
  - Each set holds ==r== read, ==w== write, ==x== execute
- `ls -l` shows ten characters before the link count
  - First: the type (`-` file, `d` directory, `l` symbolic link)
  - Then three groups of three: `rw-` `r--` `r--` is u, g, o
- `ls -ld dir` shows the directory itself, not its contents
- `stat -c '%a %A %U:%G %n' file` prints octal and symbolic side by side

```console label="Terminal"
$ ls -l /srv/project/plan.txt
-rw-r--r-- 1 root root 8 Oct 21 17:10 /srv/project/plan.txt
```

### Change owner and group
- ==`chown user:group file`== sets both; only root can change the owner
  - `chown alice file`: owner only
  - `chown :devops file`: group only
  - `chown alice: file`: owner alice, group alice's login group
  - `-R` applies it to a whole tree
- `chgrp devops file` changes only the group
  - A regular owner may move a file into any group they belong to, and no other

```console label="Terminal"
$ sudo chown alice:devops plan.txt
$ ls -l plan.txt
-rw-r--r-- 1 alice devops 8 Oct 21 17:10 plan.txt
$ sudo chown -R alice:devops /srv/project
```

```console label="Terminal (as alice)"
$ chown bob notes.txt
chown: changing ownership of 'notes.txt': Operation not permitted
$ chgrp devops notes.txt
$ chgrp bob notes.txt
chgrp: changing group of 'notes.txt': Operation not permitted
```

### chmod, symbolic form
- Who: `u`, `g`, `o`, or `a` (all three)
- Operator: `+` add, `-` remove, `=` set exactly (anything not listed is cleared)
- What: `r`, `w`, `x`
- Join changes with commas, no spaces: `chmod g+w,o-r file`
- Only the owner (or root) can chmod a file
- Symbolic form changes only what you name; the rest is left alone

```console label="Terminal (as alice)"
$ chmod g+w,o-r plan.txt
$ ls -l plan.txt
-rw-rw---- 1 alice devops 8 Oct 21 17:10 plan.txt
$ chmod u=rwx,go= plan.txt
$ ls -l plan.txt
-rwx------ 1 alice devops 8 Oct 21 17:10 plan.txt
```

- Capital ==`X`== adds execute only to directories (and to files that already have an x)
  - `chmod -R u=rwX,g=rX,o= /srv/site` makes directories `750` and files `640` in one pass
  - A lowercase `x` there would make every HTML file executable

### chmod, octal form
- Each set is one digit: ==r = 4, w = 2, x = 1==, added together
  - `rwx` 7, `rw-` 6, `r-x` 5, `r--` 4, `---` 0
- Three digits are u, g, o and always replace all nine bits
- A fourth, leading digit holds the special bits (objective 10.2)

```console label="Terminal (as alice)"
$ chmod 640 plan.txt
$ stat -c "%a %A %U:%G %n" plan.txt
640 -rw-r----- alice:devops plan.txt
$ chmod 750 .
$ stat -c "%a %A %n" .
750 drwxr-x--- .
```

| Octal | Symbolic | Typical use |
|---|---|---|
| `755` | `rwxr-xr-x` | shared directories, scripts |
| `644` | `rw-r--r--` | ordinary files |
| `750` | `rwxr-x---` | team directory, no outsiders |
| `640` | `rw-r-----` | config the group may read |
| `770` | `rwxrwx---` | group-writable project |
| `700` | `rwx------` | private directory |
| `600` | `rw-------` | private file, SSH keys |

### How the kernel decides
- Checks run in order and ==stop at the first match==
  - Owner match: only the u bits count, even if g or o are more generous
  - Group match: only the g bits count
- Root skips the rwx checks, but still needs at least one `x` bit to run a file

:::figure 1.7-permission-check.svg | Only one set of bits applies. An owner with --- is refused even when the group has rwx.

```console label="Terminal (as alice, then bob)"
$ ls -l /srv/project/plan.txt
----rwx--- 1 alice devops 8 Oct 21 17:10 /srv/project/plan.txt
$ cat /srv/project/plan.txt
cat: /srv/project/plan.txt: Permission denied
$ cat /srv/project/plan.txt
Q4 plan
```

### Directories are different
- A directory is a list of names, so the bits mean other things

:::wide
| Bit | On a file | On a directory |
|---|---|---|
| `r` | read the contents | list the names in it (`ls`) |
| `w` | change the contents | create, delete, and rename entries in it (needs `x` too) |
| `x` | run it as a program | enter it (`cd`) and reach anything inside by name |
:::

- `r` without `x`: names are visible, nothing else

```console label="Terminal (as bob; /srv/drop is 704)"
$ ls -l /srv/drop
ls: cannot access '/srv/drop/report.txt': Permission denied
total 0
-????????? ? ? ? ?            ? report.txt
```

  - `cd /srv/drop` and `cat /srv/drop/report.txt` both fail with `Permission denied`

- `x` without `r`: no listing, but a file you know the name of opens normally
- Deleting a file writes to the ==directory== that lists it
  - With `w` and `x` on the directory, bob deleted root's `report.txt`
  - With `w` on the file but not on the directory, `rm` fails: `cannot remove ... Permission denied`
- To reach a file, you need `x` on every directory in its path

:::exam
- "Members of devops can read and write in /srv/project; others have no access" is `chgrp devops`, then `chmod 770` (or `chmod g+rwx,o=`). Set ownership and mode, then check with `ls -ld`.
- A user who owns a file but has fewer rights than its group is denied. The owner set wins even when it is the most restrictive.
- Permissions are kept on disk, so they persist across reboots with no extra step. Check the parent directories too: a missing `x` on any of them blocks access.
:::
