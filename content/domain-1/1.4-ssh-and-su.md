### Access remote systems using SSH
- The objective: ==access remote systems using SSH==; ==log in and switch users in multi-user targets==
- ==SSH== (Secure Shell) gives you an encrypted shell on another host
  - Client `ssh` (`openssh-clients`); server `sshd` on TCP port 22, enabled and allowed by firewalld on RHEL 10
- `ssh alice@serverb` logs in as alice; `ssh serverb` uses your own user name
  - `ssh alice@serverb 'cmd'`: run one command and disconnect
  - `ssh -p 2222 alice@serverb`: a non-standard port
- Leave with `exit`, `logout`, or `Ctrl+D`
  - Read the prompt before every command: `[alice@serverb ~]$` is not servera
- Root password logins are refused by default (`PermitRootLogin prohibit-password`); log in as a user, then `sudo`
- Below, student already has a key for alice (topic 10.3), so no password prompt appears

```console label="Terminal"
$ ssh -o StrictHostKeyChecking=accept-new \
  alice@serverb.lab.example.com hostname
Warning: Permanently added 'serverb.lab.example.com' (ED25519) to the list of known hosts.
serverb.lab.example.com
$ ssh alice@serverb.lab.example.com 'whoami; pwd'
alice
/home/alice
```

### Host keys and known_hosts
- Every SSH server has ==host keys== in `/etc/ssh/ssh_host_*_key`
  - They prove you reached the same machine as last time
- The client saves keys it has accepted in ==~/.ssh/known_hosts==, one line per name and key type

:::figure wide 1.4-host-key-check.svg | The host key check happens before any password or key is sent. A changed key stops the connection outright.

- A first interactive connection asks before saving the key
  1. `The authenticity of host ... can't be established.` and the key's `SHA256:` fingerprint
  2. `(yes/no/[fingerprint])?`: type `yes` in full
  3. `Permanently added ...`, then the password prompt
- `-o StrictHostKeyChecking=accept-new` says yes for a new host but still refuses a changed key
- After login the client also saves the server's other key types

```console label="Terminal"
$ cut -d' ' -f1,2 ~/.ssh/known_hosts
serverb.lab.example.com ssh-ed25519
serverb.lab.example.com ssh-rsa
serverb.lab.example.com ecdsa-sha2-nistp256
$ ssh-keygen -F serverb.lab.example.com | head -1
# Host serverb.lab.example.com found: line 1
```

- `serverb` and `serverb.lab.example.com` are separate entries
  - The short name prompts again; with `-o BatchMode=yes` (no questions allowed) it simply fails
- A login that cannot authenticate is refused after the key check; ssh exits with 255

```console label="Terminal"
$ ssh -o BatchMode=yes alice@serverb hostname
Host key verification failed.
$ ssh -o BatchMode=yes \
  bob@serverb.lab.example.com true; echo $?
bob@serverb.lab.example.com: Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
255
```

### When the host key changes
- A ==changed host key== (server reinstalled, or its IP now belongs to another machine) blocks the login
  - It could also be a man-in-the-middle, so ssh refuses; the warning names the stale line
- If you know why it changed, remove the old entries with ==ssh-keygen -R== and connect again

```console label="Terminal (serverb was rebuilt)"
$ ssh alice@serverb.lab.example.com hostname
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
Offending ECDSA key in /home/student/.ssh/known_hosts:3
Host key verification failed.
$ ssh-keygen -R serverb.lab.example.com
# Host serverb.lab.example.com found: line 1
# Host serverb.lab.example.com found: line 2
# Host serverb.lab.example.com found: line 3
/home/student/.ssh/known_hosts updated.
Original contents retained as /home/student/.ssh/known_hosts.old
```

### Switching users with su and sudo
- ==su== starts a shell as another user and asks for ==that user's password==
  - No name means root; a wrong password gives `su: Authentication failure`
- `su alice` keeps your working directory and `PATH`; only `HOME`, `SHELL`, `USER`, `LOGNAME` change
- `su -` (or `su -l`) starts a ==login shell==: alice's profile, home directory, and `PATH`
  - Use the dash unless a task says otherwise; `-c 'cmd'` runs one command
- ==sudo== runs a command as root and asks for ==your own password==
  - Members of `wheel` may use it (topic 9.3); every command is logged

| Command | Becomes | Password asked | Login shell |
|---|---|---|---|
| `su alice` | alice | alice's | no |
| `su - alice` | alice | alice's | yes |
| `su -` | root | root's | yes |
| `sudo -i` | root | your own | yes |
| `sudo -i -u alice` | alice | your own | yes |

```console label="Terminal (lab system)"
$ sudo su - operator1 -c 'whoami; pwd; echo $HOME'
operator1
/home/operator1
/home/operator1
$ sudo su operator1 -c 'whoami; pwd; echo $HOME'
operator1
/home/student
/home/operator1
$ sudo -i whoami
root
```

### Multi-user targets, consoles, and who
- A server without a desktop boots to ==multi-user.target==: networking and text logins, no GUI
  - `graphical.target` adds the GNOME login screen
  - `systemctl get-default` shows which one the system boots to (changing it is topic 7.2)
- `loginctl` lists the sessions `systemd-logind` tracks (the lab VM runs Rocky Linux 10.2; `rocky` is its admin account)

```console label="Terminal (lab system)"
$ systemctl get-default
multi-user.target
$ loginctl list-sessions --no-pager
SESSION  UID USER  SEAT LEADER CLASS   TTY IDLE SINCE
      2 1000 rocky -    1901   manager -   no   -
      3 1000 rocky -    1943   user    -   no   -
```

- A login at the machine's own screen uses a ==virtual console== (VC)
  - `tty1` to `tty6`; systemd starts a `getty` login prompt on each as you switch to it

| At the console | Goes to |
|---|---|
| `Ctrl+Alt+F1` | tty1 (GNOME login, if graphical) |
| `Ctrl+Alt+F2`...`F6` | text logins on tty2 to tty6 |
| `Alt+F2` | text console to text console |
| `chvt 3` (root) | switch from a command line |

- Each VC is its own session: root on tty3 while alice stays on tty2
- Exam consoles open in a remote viewer; the same keys work, sometimes from a "send key" menu
- ==who== lists sessions: user, terminal, login time, and where from
  - `tty1` to `tty6` are local consoles; ==pts/N== is a pseudo-terminal (SSH or a terminal window)
- ==w== adds idle time and the running command (its uptime line is trimmed below)
- `whoami`, `id`, and `tty` describe your own shell

```console label="Terminal (serverb)"
$ who
alice    pts/0        2026-10-21 19:55 (172.18.0.3)
$ w -s
USER     TTY         IDLE WHAT
alice    pts/0      8.00s -bash
```

:::exam
- Tasks name the host to work on. Read the prompt before you type; a change made on the wrong host is a change the grader never sees.
- `su` versus `su -`: only the dash gives a full login environment (home, `PATH`, profile). `sudo -i` does that for root with your own password.
- `Host key verification failed.` after a rebuild is fixed with `ssh-keygen -R host`, not by deleting `known_hosts` or editing `sshd_config`.
:::
