### How key-based authentication works
- The objective: ==configure key-based authentication for SSH==
- A key pair is two matching files made together
  - The ==private key== stays on the client and proves who you are
  - The ==public key== is copied to each account you want to reach
- sshd trusts the public keys listed in the account's ==~/.ssh/authorized_keys==
  - At login it sends a challenge that only the matching private key can sign
- A ==passphrase== encrypts the private key file, so a stolen copy is useless
  - Typed on the client; never sent to the server

:::figure wide 10.3-key-auth.svg | The public key is copied once. Every later login is a challenge that only the private key can answer.

### Generating a key pair
- ==ssh-keygen== creates the pair; `-t ed25519` picks the ==Ed25519== type
  - Accept the default file name at the first prompt: `ssh` tries it automatically
  - Enter a passphrase twice, or press Enter twice for none
  - No prompts at all: `ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519`

:::wide
```console label="Terminal (alice on servera)"
$ ssh-keygen -t ed25519
Enter file in which to save the key (/home/alice/.ssh/id_ed25519):
Enter passphrase for "/home/alice/.ssh/id_ed25519" (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/alice/.ssh/id_ed25519
Your public key has been saved in /home/alice/.ssh/id_ed25519.pub
```
:::

| Path | Mode | Lives on |
|---|---|---|
| `~/.ssh/` | `700` | both hosts |
| `id_ed25519` | `600` | the client only |
| `id_ed25519.pub` | `644` | the client; copies go out |
| `authorized_keys` | `600` | the server account |

### Installing the public key
- ==ssh-copy-id user@host== appends your public key to that account's `authorized_keys`
  - Logs in once with the account's password, so password logins must still be allowed
  - Creates `~/.ssh` (`700`) and `authorized_keys` (`600`) on the server when missing
- Keys are per account: `alice@serverb` and `root@serverb` are separate lists
- Another key name: `ssh-copy-id -i key.pub` to install, `ssh -i key` to use

```console label="Terminal (alice on servera)"
$ ssh-copy-id alice@serverb
alice@serverb's password:

Number of key(s) added: 1
```

- On serverb, alice's `authorized_keys` now holds one line starting `ssh-ed25519 AAAA`

### Passphrases and ssh-agent
- With a passphrase, `ssh` asks for it on every connection
  - "passphrase for key" instead of "password" tells you the key was offered
- ==ssh-agent== holds unlocked keys for your session; ==ssh-add== loads one, `ssh-add -l` lists them

:::wide
```console label="Terminal (alice on servera)"
$ ssh alice@serverb whoami
Enter passphrase for key '/home/alice/.ssh/id_ed25519':
alice
$ eval $(ssh-agent); ssh-add; ssh-add -l; ssh alice@serverb whoami
Agent pid 1615
Enter passphrase for /home/alice/.ssh/id_ed25519:
Identity added: /home/alice/.ssh/id_ed25519 (alice@servera.lab.example.com)
256 SHA256:PGosALn+rSaSYyVv51OzATsUbFmEAiPtFJ6NTosmUJo alice@servera.lab.example.com (ED25519)
alice
```
:::

- Locking alice's password (`usermod -L`) did not stop her key login

### Server settings that persist
- `/etc/ssh/sshd_config` starts with `Include /etc/ssh/sshd_config.d/*.conf`
  - Put changes in a ==drop-in== there; files are read in name order and the ==first value wins==
  - So `10-hardening.conf` beats RHEL's own `50-redhat.conf`
- RHEL 10 defaults: `PubkeyAuthentication yes`, `PasswordAuthentication yes`, `PermitRootLogin prohibit-password` (root by key only; `sshd -T` prints it as `without-password`)

```text label="/etc/ssh/sshd_config.d/10-hardening.conf"
PasswordAuthentication no
PermitRootLogin no
```

```console label="Terminal (serverb)"
$ sudo sshd -t; echo "exit $?"
exit 0
$ sudo sshd -T | grep -E 'rootlogin|passwordauth'
permitrootlogin no
passwordauthentication no
```

1. `sudo sshd -t` checks syntax; a typo prints `Bad configuration option` with the file and line
2. `sudo systemctl restart sshd` applies it; open sessions stay connected
3. The drop-in lives in `/etc` and `sshd.service` is enabled at boot (`enabled; preset: enabled` in 4.4), so the setting is back after every reboot

- After the restart, `ssh bob@serverb` (no key) and `ssh root@serverb` (key installed) both end with `Permission denied (publickey,gssapi-keyex,gssapi-with-mic).`; alice's key still works

### When the key is ignored
- Key files that other users could change or read are refused
  - sshd's ==StrictModes== check (on by default) skips a writable `authorized_keys`
  - The login falls back to a password, or fails once passwords are off

:::wide
| Symptom | Cause | Fix |
|---|---|---|
| Password prompt although the key is installed | `authorized_keys` or `~/.ssh` writable by group or others; sshd logs `Authentication refused: bad ownership or modes` | `chmod 600` the file, `chmod 700` the directory |
| `WARNING: UNPROTECTED PRIVATE KEY FILE!` | private key readable by others (`0644`); ssh ignores it | `chmod 600 ~/.ssh/id_ed25519` |
:::

:::exam
- "User alice on servera must log in to serverb as alice without a password" is `ssh-keygen` as alice on servera, then `ssh-copy-id alice@serverb`. Test it with `ssh alice@serverb` as alice.
- Install keys before setting `PasswordAuthentication no`, or `ssh-copy-id` has no way in. Run `sshd -t` before restarting sshd.
- The first drop-in to set a value wins. If `sshd -T` still shows the old value, another file in `sshd_config.d` sets it earlier.
:::

:::try
On servera, generate an Ed25519 key pair with no passphrase for user `harry` and configure serverb so that `harry` can log in from servera with it. Then configure sshd on serverb so that root cannot log in over SSH and password logins are refused, and make sure the configuration persists across reboots.
:::
